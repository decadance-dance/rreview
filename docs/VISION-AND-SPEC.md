# rreview: vision and spec

Status: draft v0.1, 2026-11-18. Source: a research session (findings also in the Claude memory note `panel-review-research.md`). Everything marked *verified* was run on Claude Code 2.1.316, codex-cli 0.167.0, Orca 1.4.261, macOS.

## 1. Vision

`rreview <PR>` gives a pull request an independent, cross-model panel review before it is marked ready. It adapts the pipeline of [block/review](https://github.com/block/review) (Apache-2.0): fixed-lens reviewers in parallel, a coordinator that tries to disprove every candidate, and a judge that re-examines only the dropped candidates.

What makes it ours:
- **Isolated reviewers.** A reviewer sees the code, never the user's CLAUDE.md, AGENTS.md, plugins, skills, hooks or MCP, and never the reviewed PR's own `.claude/` config. Same result on any machine.
- **Read-only by the OS, not by the prompt.** Reviewers cannot write to the worktree, its git dir, or anywhere else except the run directory.
- **Cross-model.** Discovery and the judge are split across Claude and Codex, so the coordinator and the judge never share a model family.
- **Subscriptions, not API keys.** Runs on the user's Claude and ChatGPT logins through the official CLIs.
- **Visible when wanted.** The same review runs headless (default, CI-like) or with every reviewer in a visible Orca terminal, and an Orca plugin shows progress and findings.

Non-goals (v1): posting comments to GitHub, fixing findings, reviewing non-GitHub hosts, Windows, a hosted service, network isolation of reviewers beyond deny rules.

## 2. Pipeline

1. **Prepare.** Resolve the PR with `gh pr view <n> --json number,headRefName,baseRefName,title,body,url,headRefOid,baseRefOid,state,mergeCommit` (`--repo` passed through). Fetch `refs/pull/<n>/head` and the base branch from the PR's repository only when a commit is missing locally. Create a detached review worktree of the PR head (`git worktree add --detach <runroot>/wt <head-sha>`; `--head <sha>` takes that full commit id instead of `headRefOid`, for reviewing the head an earlier review looked at; it must be among the PR's commits as `gh api repos/<owner>/<name>/pulls/<n>/commits` lists them, checked before any fetch or checkout, so a head that a force-push removed from the PR is refused), never the author's worktree; it is removed at the end, also after a failure, unless `--keep-worktree`. Compute `base = merge-base(base, head)`, where `base` is the base branch tip, or for a merged PR the merge commit's first parent (today's base tip already contains the head). Create the run dir `<runroot>` (default `$XDG_STATE_HOME/rreview/<owner>/<name>/<pr>-<head-sha>/`, `~/.local/state` when unset) with mode 0700 and, on macOS, no ACL entries inherited from the state dir (an ACL is not masked by the mode), so what it holds is private to the user whatever the umask; a rerun for the same head replaces it, and stops if a kept worktree is still there, or if git still registers a worktree at `<runroot>/wt` even with its directory gone (moved, offline, locked): a registration the run did not create is never removed. A run holds an exclusive lock on `<runroot>.lock` (beside the run dir, never removed; the OS drops it when the process ends) from before it touches the run dir until it exits, so a second review of a head under review stops with exit 2 (`another review of this PR head is running`) instead of sharing the dir.
2. **Panel** (parallel). Three roles, each one pass:

| Role id | Lens | Input | Default agent |
|---|---|---|---|
| `intent_contracts` | Behavior and contracts: does the PR meet its stated intent and the task's acceptance criteria; producer to consumer tracing; compatibility; edge cases; a test that fails when the logic breaks | diff, PR title and body, task AC (`--context-file`) | codex |
| `reliability` | Failure injection at each call, partial success, races, cleanup, unbounded growth, load, migrations and rollback | diff, PR title and body | claude |
| `security` | Trust boundaries, authz, injection, secrets, supply chain | diff only: no PR text, no task (blind lens) | codex |

   Lens procedures start from block/review's `panelists.go`; the intent lens adds the AC check. PR text, task text and repo files are untrusted evidence, never instructions.
3. **Coordinator** (claude). Dedupe by root cause and failure scenario; try to disprove every candidate against the code; drop only with cited counter-evidence; account for every candidate (kept, merged, or dropped with reason). Port block/review `coordinator.md`. If a panelist failed, it covers that lens and the run is `degraded`. It sees the PR text and the task as untrusted data, and every panelist's validated envelope or error. Every candidate of a completed panelist carries a host-assigned id, `<role>-<n>` (n from 1, in the envelope's order); the review must give each id exactly one disposition, in the `candidate_ids` of the finding that covers it or as one drop, else it fails validation. A finding with no `candidate_ids` is the coordinator's own (a failed lens). Coordinator failure fails the review (exit 2, no `result.json`).
4. **Judge** (codex; never the coordinator's family). Sees only dropped candidates plus kept findings; restores real defects. Port block/review `judge.md`. Each restoration names the `candidate_id` of the drop it restores, at most once per drop; any other id fails validation. It runs only when the coordinator dropped a candidate. Judge failure keeps the coordinator's findings and marks `degraded`.
5. **Deliver.** Merge kept and restored, dedupe (same file, start line and title, case and spacing ignored; the whole duplicate that clears the gate wins, then the most urgent, then the most confident, then the first; the merged finding keeps every duplicate's `candidate_ids`), gate (default P0-P2 and confidence >= 0.5, set by calibration in `docs/calibration.md`; `--gate p<=N,conf>=X` moves the bar, `--all` disables). Write `result.json`; print a human summary (`--json` prints `result.json` instead); exit code 0 = no gated findings, 1 = gated findings, 2 = review failed.

Role-to-agent mapping is configurable per role (`--role-agent security=claude`), with a `--author claude|codex` shortcut (default `claude`) that flips the defaults so most discovery and the judge use the other family. A mapping that gives the coordinator and the judge the same family is refused before any work, with exit 2. `--role-model` and `--role-effort` set a role's model (`claude --model`, `codex -m`) and reasoning effort (`claude --effort`: low, medium, high, xhigh, max; `codex -c model_reasoning_effort=`: minimal, low, medium, high, xhigh); unset, the CLI's own default applies.

## 3. Isolation and sandbox (the security core)

**Claude passes** run `claude` with:
- `--safe-mode`: disables CLAUDE.md, skills, plugins, hooks, MCP, agents (user and project scope). *Verified*, including a hostile project hook that did not fire. `--bare` is not usable: it needs an API key.
- `--settings <runroot>/claude-settings.json`, generated per run with **absolute paths only** (a relative `./` in a `--settings` file does not anchor at cwd; *verified* that it let a write through):

```json
{
  "permissions": { "deny": ["Edit", "Write", "NotebookEdit", "mcp__*", "Bash(gh *)", "Bash(git push*)", "Bash(curl *)", "Bash(wget *)", "WebSearch", "WebFetch"] },
  "sandbox": {
    "enabled": true, "autoAllowBashIfSandboxed": true, "allowUnsandboxedCommands": false,
    "filesystem": { "denyWrite": ["<abs worktree>", "<abs git common dir>"], "allowWrite": ["<abs runroot>/scratch/<role>/out"] }
  },
  "disableBundledSkills": true
}
```
- Each pass gets its own launch dir `<runroot>/scratch/<role>/`: this settings file and the one dir it may write (`out/`). No pass can write into another pass's dir or into `<runroot>/out`, where the host keeps validated replies.
- Without the git common dir in `denyWrite`, `git commit` and `git branch` succeed from the worktree (*verified*).
- `sandbox.network.allowedDomains` did not block `curl` (*verified*); the deny rules above are the network fallback. Open item.
- Session transcripts: a reviewer pass leaves its normal session transcript in the user's Claude config dir (`$CLAUDE_CONFIG_DIR` or `~/.claude`). Accepted: a run-scoped config dir has no login, and `--no-session-persistence` would rule out the wrap-up, which resumes the session (`--session-id <uuid>`, then `--resume <uuid>`). rreview never edits the user's config dir.

**Codex passes** run `codex exec --json -s read-only -C <worktree> -o <runroot>/scratch/<role>/replies/reply.txt` (stdout is Codex's JSONL event log: the commands it ran and their output) with `CODEX_HOME=<runroot>/scratch/<role>/codex-home`, a fresh dir holding only a symlink to the user's `auth.json`. Not `--ephemeral`: the wrap-up resumes the session (`codex exec <same options> resume <thread-id> -`), so the session is kept, in that run-scoped home only. A resume with the exec-level `-s read-only -C` keeps the sandbox (*verified*: a write into the repo got "Operation not permitted"). The reply file is in the pass's own dir, which no other pass can write: Codex writes it itself, outside its sandbox, and would follow a symlink planted there. A turn that exits 0 without writing it is an empty reply, which fails validation and so gets the retry turn. `--ignore-user-config` alone still loads `~/.codex/AGENTS.md` (*verified*); the clean home does not (*verified*). Open items: `-m gpt-6.1-sol` was rejected in a clean home with a ChatGPT login (default became `gpt-6-luna`); whether token refresh replaces the symlink.

**Environment.** A reviewer inherits only what its CLI needs to run and log in: `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR` (find the login, including the macOS keychain; give the sandboxed shell a shell and a temp dir), `LANG`, `LC_ALL`, `LC_CTYPE`, `LC_COLLATE`, `LC_MESSAGES`, `LC_MONETARY`, `LC_NUMERIC`, `LC_TIME`, `TZ`, `TERM`, `COLORTERM` (locale; the TUI under the orca runner), `HTTPS_PROXY`, `NO_PROXY` (either case), `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE` (reach the API from a proxied network); Claude also `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_OAUTH_TOKEN` (its subscription login); Codex gets only its run-scoped `CODEX_HOME` from rreview. Not `ANTHROPIC_API_KEY`: Claude Code then reports `api_key` instead of `claude.ai` and bills the API (§1). Credentials that do reach the CLI, and so the reviewer, when the user sets them: a proxy URL's user and password, and the Claude OAuth token. Everything else, such as a `GH_TOKEN` set for rreview's `gh`, is dropped. Headless: the CLI starts with a cleared environment plus the listed names. Orca: the terminal's environment is Orca's and its login shell's, not rreview's, and a shell cannot drop all of it (a read-only export, a name that is no identifier, an exported function; zsh aborts the line on `unset` of a read-only variable), so the agent starts through a shim `<runroot>/scratch/<role>/bin/<program>` (a `/bin/sh` script, outside every pass's writable dir) that enters the launch's working dir and hands it to the hidden `rreview exec-reviewer --inherit <name> ... --set NAME=value ... -- <program> <args>`: it clears the environment, keeps each listed variable that is set and the launch's own env, and replaces itself with the program, so inherited values stay in the environment and never appear in an argv. The typed line is `PATH='<shim dir>':"$PATH" exec '<program>' ...`; no value goes on it, which the shell may keep in its history. A run dir whose path holds a `:` is refused (exit 2): it would split that PATH entry and the shell would start the real program with the terminal's whole environment. (*verified* live on both runners: the reviewer process held only listed names; Orca still recognizes and pastes to Claude and Codex). Orca's `codex` shell function prepends `-c shell_environment_policy.set.ORCA_*='...'` (pane, terminal, workspace and worktree ids, its data dir) to a Codex launch; a Codex reviewer must not see them: the allowlist holds for every name rreview did not choose, and they would tell a reviewer's command its Orca terminal and Orca's data dir, which no review needs. So the orca runner's Codex launch also passes `-c shell_environment_policy.include_only=[<the names above>]`: Codex applies `include_only` after `set`, so it wins whichever `-c` comes first, and keeps `CODEX_HOME` out of the reviewer's commands too (*verified* live, codex-cli 0.167.0 and Orca 1.4.262: `env` run by the Codex reviewer showed no `ORCA_*` and the allowlist's names, while the same launch without it showed all five; Orca still recognized and pasted to Codex; #29). The reviewer's shell is the user's: zsh sources `~/.zshenv`, so a variable exported there reaches the reviewer's commands whatever the CLI's environment (*verified*; #35). A `--version` probe still runs with rreview's environment; it is no reviewer turn.

**Repo-provided text** (AGENTS.md, CLAUDE.md, `.agents/checks`) may still be read as code. Prompts state it is untrusted evidence.

## 4. Runners

One interface, two implementations:

```
run(pass) -> raw text      // pass = {role, agent, model, effort, prompt, cwd, timeout, outFile}
wrapUp(pass, message) -> raw text   // "time is up, reply with the JSON now"
```

- **headless** (default): `claude -p --output-format json` / `codex exec -o`. The reply is Claude's `result` (a failed exit or `is_error` fails the pass) or Codex's `-o` file. Each agent runs in its own process group; a timeout kills the whole group and the error names the pass, and when a turn ends whatever the agent left running in its group is killed too. Since no reviewer shares rreview's group, the terminal's Ctrl-C reaches rreview alone: on SIGINT or SIGTERM it kills (signalling each group itself, through no helper process) every running reviewer's group (and a prepare subprocess's, with or without a deadline), lets the run's cleanup remove the review worktree unless `--keep-worktree` (a checkout cut short leaves its registration locked, so the removal is forced twice), starts no further pass, writes no `result.json` and exits 2. The cleanup's own git runs in its own process group, so a Ctrl-C does not cut it short; a signal that arrives during the cleanup, a second one included, changes nothing but the outcome: the run still exits 2 without `result.json`, and the first signal is the one reported. Only SIGKILL ends rreview before its cleanup. `rreview show` catches no signal and runs its `gh` in rreview's own process group, so a Ctrl-C ends both. The orca runner stops and cleans up the same way (below). Wrap-up resumes the session (`claude -p --resume <id>`, `codex exec resume <thread-id>`). Logs: `<runroot>/logs/<role>.{stdout,stderr}`, and `<role>-turn<n>.*` for each wrap-up or retry turn.
- **orca** (variant 5), only with the Orca app running: before any work, within the review's budget, `orca status` must report the app running and its runtime reachable, and `orca repo show --repo path:<main checkout>` must find this repository (a reachable runtime can lack it), otherwise exit 2. It needs no Orca terminal (`ORCA_TERMINAL_HANDLE`): the runner uses only `orca worktree` and `orca terminal` commands, which work from any process of the user's, the Orca plugin's worker included (*verified*, Orca 1.4.262). The review worktree is Orca-created: `orca worktree create --repo path:<main checkout> --name rreview-<pr>-<sha12>-<pid>-<unix-seconds> --branch rreview/<same> --base-branch <head-sha> --setup skip` (setup hooks would run the PR's code), within the review's budget. The pid and start time make the name the run's own, so two runs for one PR head in one repository never share a worktree or branch, and neither run's cleanup reaches the other's. That branch must not exist before the run (a leftover stops it; the check is a preparation step, within the budget and stopped by a signal), so whatever carries it afterwards is the run's own: the cleanup guard is armed just before the create starts and finds the worktree through `git worktree list` by that branch, so a create whose reply was lost is cleaned up too. A create Orca did not confirm may still be finished by the app: any failed create counts, as none proves Orca refused it (its CLI killed at its deadline, no JSON reply, or an error such as the CLI's own transport timeout `runtime_timeout`), so the cleanup waits up to 30 s for its worktree to appear, and closing the terminals a failed `terminal create` may have opened waits the same way after a failed one; each `terminal list` of that wait gets only what is left of its 30 s, and a warning names the worktree's branch or the terminal's title when nothing appeared; those terminals are found by their tab's title in `orca terminal list --include-visual-layouts` (the title `--title` sets; a list row's own title can be the one the running program set) and closed by their panes' handles; the host checks the worktree's HEAD and that Orca made the requested branch. Removal: `orca worktree rm --force` (`git worktree remove --force` for a worktree Orca never registered), then `git branch -D` of that branch, unless `--keep-worktree`. Per pass, in its own `<runroot>/scratch/<role>` as for headless: `orca terminal create --worktree path:<wt> --title rreview:<role> --command "PATH='<scratch>/bin':\"$PATH\" exec '<program>' '<arg>' ..."` (the same isolated command, interactive, every word single-quoted, through the §3 environment shim; the program must be `exec`'s first word: with `exec env ...` or `exec '<path>/<program>'` Orca names the agent but its `send` reports provider `unsupported` and types the prompt raw, *verified*); `orca terminal show` until Orca reports the pass's agent as the terminal's `agentIdentity`, then `orca terminal wait --for tui-idle`, in slices of at most 10 s (each slice is Orca's `--timeout-ms`; the call itself is bounded only by the turn's deadline, so a slow CLI's late answer still counts, and Orca's transport timeout `runtime_timeout` ends only the slice); after each slice that times out, `orca terminal show`: a dialog (`agentWait`) open for 30 s fails the pass at once, as `blockedReason` does; one the agent clears sooner is waited out. At the turn's deadline one more look, within the wait's 5 s backstop: a dialog still open then fails the turn as a dialog, not as a timeout (the wrap-up and the retry included); a look the deadline cuts short is a timeout, whatever an earlier look saw, so the wrap-up looks again before it types. Before every prompt (the first, the reminder, the wrap-up, the retry) the same check runs, and a dialog still open after 30 s or at the deadline fails the turn with nothing typed: Enter would answer it. rreview never answers a permission dialog (#28). Nothing is typed before that: until Orca recognizes the agent it types text raw, into the shell before the agent starts and with every newline an Enter afterwards (*verified*: a starting Codex TUI satisfied `tui-idle` before Orca recognized it, and a prompt sent then arrived as raw lines; `send` reported `provider: unsupported`, which the runner now treats as a failure). `exec` leaves no shell behind the agent. `orca terminal send --text <message> --enter`; `wait --for tui-idle` again; then read `scratch/<role>/out/reply.txt`, which the reviewer writes itself (it may write only that `out/`; a symlink or FIFO there is refused); the host validates it and publishes `<runroot>/out/<role>.json`. The message starts with the delivery instruction, before the prompt, whose last part is the PR's untrusted text; control bytes are dropped from it. An agent idle without the file gets one reminder, then the pass fails. Each phase (first turn, wrap-up, retry) has one absolute deadline that bounds every Orca call in it, `send` included (an Orca call still running at the deadline is killed); a `wait` answer that arrives after the deadline counts as a timeout, whatever it says. At the pass timeout the wrap-up is typed into the same terminal; a reply that fails validation gets its retry turn there too; a wrap-up or retry past its own timeout closes the terminal and fails the pass. A terminal stays open between turns; it closes when its pass fails, else when the run ends, and one whose close fails stays registered and is closed again at the end. On SIGINT or SIGTERM the Orca call a pass waits on (`terminal show`, `wait`, `send`) is killed with its process group, signalled by rreview itself, and the pass fails; no worktree or terminal is created after the signal, while a `worktree create` or `terminal create` already running is waited for within its deadline, as the app may finish one whose CLI was killed; one killed at that deadline gets the 30 s wait above. Then the run closes every terminal it opened and removes its worktree and branch unless `--keep-worktree`, each `orca` and `git` call of that cleanup in its own process group and run to its end, so a Ctrl-C cannot cut it short; it exits 2 as headless does. Do **not** use `orchestration worker-start`/`worker_done`: `worker_done` cannot reach the Orca runtime from inside the sandbox (EPERM, *verified*).
  - Claude's trust dialog shows in an Orca-created worktree too, unless the repository's main checkout is already trusted (*verified*, Orca 1.4.262 with a per-account Claude config); `wait` reports it as `blockedReason: agent-trust-workspace`, and the runner answers "Yes, I trust this folder" once, before the prompt. That matches headless `claude -p`, which skips the dialog; `--safe-mode` still keeps out the worktree's project customizations. Known limit: the answer persists in the user's Claude config (`.claude.json` under `$CLAUDE_CONFIG_DIR` or `~`, a `hasTrustDialogAccepted` project entry), so later Claude sessions there skip the dialog as well. Orca has a per-repository `agentWorkspaceTrust: pre-trust` setting, but neither `orca repo set` nor `orca worktree create` exposes it, and pre-trusting writes the same entry.
  - Claude runs with the §3 settings plus `--permission-mode acceptEdits --add-dir <scratch>/out`: the reply is a sandboxed Bash redirect into `out/`, which Claude otherwise asks about. Not `dontAsk`: on a live pass it refused the reviewer's heredoc reply twice (*verified*). `tui-idle` does not report a permission dialog as blocked: it only times out, while `orca terminal show` reports the dialog as the terminal's `agentWait` (*verified*: a WebSearch, now denied in §3, and the reply heredoc below). Claude asks about the reply heredoc when it holds a JSON object ("Contains brace with quote character"), in some runs clearing the dialog itself within seconds (*verified*); delivering the reply without a Bash command: #37. The deny rules remove Edit and Write, and the sandbox refuses every write outside `out/` (*verified* live in this launch mode: Edit and Write were absent; `git commit`, `git branch` and writes into the worktree and `$HOME` failed with EPERM).
  - Codex's `-s read-only` blocks every write, the reply file too. The Codex TUI runs `codex -C <scratch>/out -s workspace-write -a never -c sandbox_workspace_write.exclude_slash_tmp=true -c sandbox_workspace_write.exclude_tmpdir_env_var=true` (and the §3 `include_only`) in the pass's clean `CODEX_HOME`: `out/` is its only writable root, it reads the worktree by absolute path, and `-a never` returns a refused command instead of asking (*verified* live in this launch mode: writes into the worktree, the git common dir, `$HOME` and `/tmp`, `git commit` and `git branch` failed; a write into `out/` worked; the user's `~/.codex/AGENTS.md` did not reach the session). Inside a git checkout the Codex TUI stops at its own trust prompt, which rreview does not answer, so a run with a Codex pass refuses a run dir inside a checkout (set `XDG_STATE_HOME` elsewhere).

Panel passes run in parallel (max 3, one thread each); coordinator and judge run in sequence. Budget: a per-pass timeout (`--timeout`, default 900 s) plus a total budget (`--budget`, default 3600 s); the budget starts before preparation, whose subprocesses (`gh`, `git` fetch and checkout, version probes) run in their own process group, killed at the deadline, and do not start after it (exit 2); every pass's timeout, wrap-up and retry are capped at what is left of the budget, and a pass with no budget left does not start (it fails). A pass killed at its timeout gets one wrap-up turn (at most 180 s). A reply that fails validation gets one more turn, which resumes the session with the validation error (at most 180 s); a CLI that failed (exit status, Claude's `is_error`) is not retried. After that the pass has failed.

## 5. Data contract

All outputs live in `<runroot>`, written by one run at a time (the `<runroot>.lock` of §2); a review prints `run id: <id>` and `run dir: <runroot>` to stderr as soon as the dir exists, before any pass, and the run dir again at the end:
- `meta.json`: `run_id` (that id, `<pid>-<unix nanos>`, unique to the run), PR, base, head, runner, role-to-agent map, versions of claude/codex; written before the review worktree, so a run stopped while making it still names its run dir.
- `progress.jsonl`: one line per event `{ts, role, status: started|wrapup|retry|completed|failed, agent, model, duration_ms, error?}`; `ts` is Unix epoch milliseconds, `duration_ms` counts from the pass's start, `model` is the role's `--role-model` or `default`. A `retry` event's `error` is the validation error that caused it. Roles: `intent_contracts`, `reliability`, `security`, `coordinator`, `judge`. A run that SIGINT or SIGTERM stopped (§4) ends it with `{ts, role: "run", status: "interrupted", error}` once its cleanup is done, `error` naming the signal; a pass the signal cut short is `failed` with the same error. The plugin tails it.
- `out/<role>.json`: the validated reviewer JSON (panelist envelope, coordinator review, judge array) following block/review's shapes (`panelistShape`, finding schema with `title`, `body`, `priority` 0-3, `confidence_score`, `code_location`), normalized by the host. It exists only for a pass whose reply passed validation. `out/` belongs to the host: reviewers write only into their own `scratch/<role>/`, so no pass can touch another's published reply. A panelist candidate locates itself with `path`, `line_start`, `line_end`.
- Coordinator reply: `{findings: [{title, body, confidence_score, priority, code_location, candidate_ids}], dropped_candidates: [{candidate_id, drop_reason: disproved|speculative|deterministic_ci|below_bar, evidence}], overall_correctness, overall_explanation, overall_confidence_score, review_process}`. Judge reply: `[{candidate_id, title, body, confidence_score, priority, code_location}]`.
- `result.json`: `{findings, ungated_findings, dropped_candidates, overall_correctness, overall_explanation, review_process, base, head, passes, degraded}` (block/review `Result`), written only when the coordinator completed. A finding is `{title, body, file, start_line, end_line, priority, confidence_score, stage: coordinator|judge, candidate_ids}` with a repo-relative `file` and the `[Pn]` tag cut from the title; a dropped candidate is `{id, title, panelist, file, line_range, priority, confidence_score, claim, drop_reason, evidence}`, filled by the host from the panel candidate plus the coordinator's reason and evidence; a pass is `{role, agent, model, effort?, status: completed|failed, duration_ms, error?}`. `degraded` is true when a panelist or the judge failed.
- Validation: strict decoding of the whole reply against its declared shape (an object for an envelope or review, an array for the judge), bare or inside one ```` ```json ```` fence with prose around it, nothing else; unknown fields rejected; one malformed candidate rejects the envelope; paths must be repo-relative and inside the diff's files (`git diff --name-only base head`, matched exactly). The same holds for the coordinator's review and the judge's array: a finding's `code_location.absolute_file_path` may also be an absolute path inside the review worktree; `priority` and `confidence_score` are required; a struct sent as a positional array or a repeated key is rejected.

## 6. CLI

```
rreview <pr-number|url> [--repo owner/name] [--head sha] [--runner headless|orca] [--author claude|codex]
        [--role-agent role=agent]... [--role-model role=model]... [--role-effort role=effort]...
        [--context-file path] [--gate p<=2,conf>=0.5 | --all] [--json] [--keep-worktree]
        [--timeout secs] [--budget secs] [--only role]
rreview show <runroot|pr> [--repo owner/name] [--json]   # print result of the latest run
rreview doctor [--runner headless|orca]   # claude/codex/gh/orca versions, logins, sandbox self-test
```

`--timeout` is the per-pass timeout (default 900 s); a pass that hits it gets one wrap-up turn of at most 180 s. `--budget` is the whole review's (default 3600 s). `--head` reviews that commit (a full id, one of the PR's commits; GitHub lists at most 250) instead of the PR's current head; the run dir is named after it. A missing commit is fetched with the whole PR ref and base branch, which brings the PR's later commits into the repository too; so does resolving a merged PR's base, which needs the merge commit. A review that must not see later commits needs the head and base commits present beforehand and, for a merged PR, `gh pr view` answering with the pre-merge base as an open PR would; `docs/calibration.md` shows how. `--context-file` is the task's acceptance criteria, read by the intent lens and the coordinator. `--only <role>` runs one panelist alone, without coordinator, judge or `result.json` (a development flag; exit 0 when it completed, else 2). `--runner` takes only `headless` until the Orca runner lands. `rreview show` reads `<runroot>/result.json`, or for a PR the newest `result.json` among its run dirs, and prints it like the review did, with the same exit code.

`rreview doctor` runs the isolation self-test on a throwaway repo and a detached worktree of it, through the same launch builders a review uses: a write into the worktree, a commit and a branch must fail, `git diff` must work, a planted project hook must not fire, Claude's Write and Edit tools must not change the worktree, and Claude Code's own session transcript for the worktree must show each of them not offered to the model or its call refused (an unchanged worktree alone passes when Claude never tried; no transcript record fails the check), Codex must not load the user's AGENTS.md. Checks need the effects on disk and tool-side evidence to agree, never the reviewer's reply alone: Claude's probe writes its exit codes to `out/`, Codex's run must show the probe in its `--json` event log. The planted hook has a positive control at no model cost: the same Claude launch without `--safe-mode` and with an empty `CLAUDE_CONFIG_DIR` (no user config, no login) must fire it. The AGENTS.md probe gives Codex a stand-in `HOME` whose `.codex/AGENTS.md` names a random canary that must not appear in the reply, plus a control run whose clean `CODEX_HOME` holds a canary that must appear; the user's own `~/.codex` and `~/.claude` are never touched (but see `--runner orca`). `--runner orca` also runs the self-test through the orca runner (§4), so through `claude_tui`, `codex_tui` and the §3 shim, on a second throwaway repo, and only from an Orca terminal (`ORCA_TERMINAL_HANDLE` set); elsewhere that part prints a `skip` line and does not fail. Orca opens terminals only in a worktree it tracks, so the reviewers' terminals open in the caller's Orca worktree (`--worktree current`), titled `rreview:<role>:<run tag>`; no teardown removes that worktree, so a terminal whose `terminal create` reply was lost is found by its title and closed and the shim enters the throwaway worktree (the launch's working dir) before it starts the agent. Claude: the same probe and checks as headless; its probe sits in `out/` (a Read elsewhere stops the TUI at a permission dialog) and its reply, as the delivery line and the runner's reminder name it, is the probe's output line, not JSON (a heredoc holding `{"` stopped it at a "brace with quote character" dialog, *verified*, Claude Code 2.1.316). Codex: a probe writes into the worktree, the git common dir and the stand-in `HOME` and records its exit codes in `out/`, which must agree with the disk (the TUI has no `--json` event log, so this rests on that report and the disk); this check depends on the Codex model agreeing to run a script that tries writes outside its workspace: the prompt says the writes are meant to fail, a Codex that declines gets one reminder (in the same session, or in a new one when it refused in chat without a reply file and its pass failed), and one that still declines fails the check with "the probe did not run" (it declined in 5 of 6 live runs, codex-cli 0.167.0; neither Codex's `!` shell, which runs unsandboxed, nor `codex sandbox`, which ignores the TUI's tmp excludes, can stand in for it; #31); the AGENTS.md canary and its control run as headless, the control in an Orca terminal of its own. Known limit: the runner answers Claude's trust dialog for the throwaway worktree, which is recorded in the user's Claude config, as in a review (§4), and the TUI session leaves its transcript there (§3). A fixture whose checks all passed is removed; a failed one is kept as evidence, and doctor prints its path and the command that removes it. It prints one line per check (`ok`, `FAIL`, `skip`, or `warn` for the optional `orca`, which `--runner orca` requires in an Orca terminal) and exits 0 only when every required check passes, else 1. This turns section 3's *verified* facts into a check that runs on every machine and every CLI upgrade.

## 7. Orca plugin (variant 6), after the CLI

A `trusted-worker` plugin in `orca-plugin/` (TypeScript, no build step; Node `child_process`/`fs` in its worker; confirmed in community plugins `klcd/agent-cli-permissions` and `Geromendez135/orca-pr-review`):
- Panel: the PR of the focused workspace (`gh pr view` in its folder, or a PR number or URL typed into the panel), button "Run review", runner choice (headless or orca).
- The worker runs `rreview <pr-url> --runner <r> --json` as a child process in the workspace's folder, learns the run id and dir from the first `run id:` and `run dir:` lines on stderr, tails `progress.jsonl`, and takes the result from the exit code and the JSON on stdout (exit 2, a signal, or stdout that is not a valid result is a failed review); it renders findings as a file tree with line findings (UI pattern from `orca-pr-review`, MIT). The worker's environment is Orca's, not a terminal's: no `ORCA_TERMINAL_HANDLE`, which the orca runner does not need (§4). An optional GitHub account setting passes that `gh` account's token as `GH_TOKEN` to the gh and rreview child processes only.
- "Cancel" names the run the panel shows (a token unique to the run, set before rreview starts; not its start time, which a clock set back can repeat) and is refused for any other; it sends the running rreview SIGTERM, on which rreview cleans up (§4) and exits 2. The run shows as cancelled only when rreview reports the stop: the `run` stop line of `progress.jsonl`, or, stopped before it had a run dir, its `error: … interrupted by SIGTERM` line; one that ended with a result first stays done, and one that failed on its own shows its error. A run still going 70 minutes after it started gets SIGTERM too and shows as failed, unless a Cancel was already sent. A SIGTERM'd rreview still running 10 minutes later is killed, which skips what is left of its cleanup.
- Progress is read only while the run dir is still this run's (its `meta.json` names the run id; a rerun for the same head may recreate the dir with the same path and inode), one bounded read at a time. Posts and stored state carry the run's status and counts only; the panel fetches the result, cut to Orca's message limits, and the full text stays in `result.json`.
- "Send to author": the person chooses an agent of the reviewed run's workspace (`agents.list`). The worker writes the selected findings, marked as review evidence, to `<runroot>/author-<time>.md`, refuses unless that terminal still runs the same agent session (`sessionId`) in that workspace, and types one fixed line naming the file with the worker's host API `terminal.sendText` (capability `terminal:send`); reviewer text is never typed into a terminal. This is not an orchestration send, so it needs no `--from`.

## 8. Milestones
