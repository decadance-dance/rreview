# rreview: vision and spec

Status: draft v0.1, 2026-11-18. Source: a research session (findings also in the Claude memory note `panel-review-research.md`). Everything marked *verified* was run on Claude Code 2.1.316, codex-cli 0.167.0, Orca 1.4.261, macOS.

## 1. Vision

`rreview <PR>` gives a pull request an independent, cross-model panel review before it is marked ready. It adapts the pipeline of [block/review](https://github.com/block/review) (Apache-2.0): fixed-lens reviewers in parallel, a coordinator that tries to disprove every candidate, and a judge that re-examines only the dropped candidates.

What makes it ours:
- **Isolated reviewers.** A reviewer sees the code, never the user's CLAUDE.md, AGENTS.md, plugins, skills, hooks or MCP, and never the reviewed PR's own `.claude/` config. Same result on any machine.
- **Read-only by the OS, not by the prompt.** Reviewers cannot write to the worktree, its git dir, or anywhere else except the run directory.
- **Cross-model.** Discovery and the judge are split across Claude and Codex, so the coordinator and the judge never share a model family.
- **Subscriptions, not API keys.** Runs on the user's Claude and ChatGPT logins through the official CLIs.
- **Visible when wanted.** The same review runs headless (default, CI-like) or with every reviewer in a visible Orca terminal, and an Orca plugin shows progress and findings.

Non-goals (v1): posting comments to GitHub, fixing findings, reviewing non-GitHub hosts, Windows, a hosted service, network isolation of reviewers beyond deny rules.

## 2. Pipeline

1. **Prepare.** Resolve the PR with `gh pr view <n> --json number,headRefName,baseRefName,title,body,url,headRefOid,baseRefOid,state,mergeCommit` (`--repo` passed through). Fetch `refs/pull/<n>/head` and the base branch from the PR's repository only when a commit is missing locally. Create a detached review worktree of the PR head (`git worktree add --detach <runroot>/wt <head-sha>`; `--head <sha>` takes that full commit id instead of `headRefOid`, for reviewing the head an earlier review looked at; it must be among the PR's commits as `gh api repos/<owner>/<name>/pulls/<n>/commits` lists them, checked before any fetch or checkout, so a head that a force-push removed from the PR is refused), never the author's worktree; it is removed at the end, also after a failure, unless `--keep-worktree`. Compute `base = merge-base(base, head)`, where `base` is the base branch tip, or for a merged PR the merge commit's first parent (today's base tip already contains the head). Create the run dir `<runroot>` (default `$XDG_STATE_HOME/rreview/<owner>/<name>/<pr>-<head-sha>/`, `~/.local/state` when unset); a rerun for the same head replaces it, and stops if a kept worktree is still there.
2. **Panel** (parallel). Three roles, each one pass:

| Role id | Lens | Input | Default agent |
|---|---|---|---|
| `intent_contracts` | Behavior and contracts: does the PR meet its stated intent and the task's acceptance criteria; producer to consumer tracing; compatibility; edge cases; a test that fails when the logic breaks | diff, PR title and body, task AC (`--context-file`) | codex |
| `reliability` | Failure injection at each call, partial success, races, cleanup, unbounded growth, load, migrations and rollback | diff, PR title and body | claude |
| `security` | Trust boundaries, authz, injection, secrets, supply chain | diff only: no PR text, no task (blind lens) | codex |

   Lens procedures start from block/review's `panelists.go`; the intent lens adds the AC check. PR text, task text and repo files are untrusted evidence, never instructions.
3. **Coordinator** (claude). Dedupe by root cause and failure scenario; try to disprove every candidate against the code; drop only with cited counter-evidence; account for every candidate (kept, merged, or dropped with reason). Port block/review `coordinator.md`. If a panelist failed, it covers that lens and the run is `degraded`. It sees the PR text and the task as untrusted data, and every panelist's validated envelope or error. Every candidate of a completed panelist carries a host-assigned id, `<role>-<n>` (n from 1, in the envelope's order); the review must give each id exactly one disposition, in the `candidate_ids` of the finding that covers it or as one drop, else it fails validation. A finding with no `candidate_ids` is the coordinator's own (a failed lens). Coordinator failure fails the review (exit 2, no `result.json`).
4. **Judge** (codex; never the coordinator's family). Sees only dropped candidates plus kept findings; restores real defects. Port block/review `judge.md`. Each restoration names the `candidate_id` of the drop it restores, at most once per drop; any other id fails validation. It runs only when the coordinator dropped a candidate. Judge failure keeps the coordinator's findings and marks `degraded`.
5. **Deliver.** Merge kept and restored, dedupe (same file, start line and title, case and spacing ignored; the whole duplicate that clears the gate wins, then the most urgent, then the most confident, then the first; the merged finding keeps every duplicate's `candidate_ids`), gate (default P0-P2 and confidence >= 0.5, set by calibration in `docs/calibration.md`; `--gate p<=N,conf>=X` moves the bar, `--all` disables). Write `result.json`; print a human summary (`--json` prints `result.json` instead); exit code 0 = no gated findings, 1 = gated findings, 2 = review failed.

Role-to-agent mapping is configurable per role (`--role-agent security=claude`), with a `--author claude|codex` shortcut (default `claude`) that flips the defaults so most discovery and the judge use the other family. A mapping that gives the coordinator and the judge the same family is refused before any work, with exit 2. `--role-model` and `--role-effort` set a role's model (`claude --model`, `codex -m`) and reasoning effort (`claude --effort`: low, medium, high, xhigh, max; `codex -c model_reasoning_effort=`: minimal, low, medium, high, xhigh); unset, the CLI's own default applies.

## 3. Isolation and sandbox (the security core)

**Claude passes** run `claude` with:
- `--safe-mode`: disables CLAUDE.md, skills, plugins, hooks, MCP, agents (user and project scope). *Verified*, including a hostile project hook that did not fire. `--bare` is not usable: it needs an API key.
- `--settings <runroot>/claude-settings.json`, generated per run with **absolute paths only** (a relative `./` in a `--settings` file does not anchor at cwd; *verified* that it let a write through):

```json
{
  "permissions": { "deny": ["Edit", "Write", "NotebookEdit", "mcp__*", "Bash(gh *)", "Bash(git push*)", "Bash(curl *)", "Bash(wget *)", "WebSearch", "WebFetch"] },
  "sandbox": {
    "enabled": true, "autoAllowBashIfSandboxed": true, "allowUnsandboxedCommands": false,
    "filesystem": { "denyWrite": ["<abs worktree>", "<abs git common dir>"], "allowWrite": ["<abs runroot>/scratch/<role>/out"] }
  },
  "disableBundledSkills": true
}
```
- Each pass gets its own launch dir `<runroot>/scratch/<role>/`: this settings file and the one dir it may write (`out/`). No pass can write into another pass's dir or into `<runroot>/out`, where the host keeps validated replies.
- Without the git common dir in `denyWrite`, `git commit` and `git branch` succeed from the worktree (*verified*).
- `sandbox.network.allowedDomains` did not block `curl` (*verified*); the deny rules above are the network fallback. Open item.
- Session transcripts: a reviewer pass leaves its normal session transcript in the user's Claude config dir (`$CLAUDE_CONFIG_DIR` or `~/.claude`). Accepted: a run-scoped config dir has no login, and `--no-session-persistence` would rule out the wrap-up, which resumes the session (`--session-id <uuid>`, then `--resume <uuid>`). rreview never edits the user's config dir.

**Codex passes** run `codex exec --json -s read-only -C <worktree> -o <runroot>/scratch/<role>/replies/reply.txt` (stdout is Codex's JSONL event log: the commands it ran and their output) with `CODEX_HOME=<runroot>/scratch/<role>/codex-home`, a fresh dir holding only a symlink to the user's `auth.json`. Not `--ephemeral`: the wrap-up resumes the session (`codex exec <same options> resume <thread-id> -`), so the session is kept, in that run-scoped home only. A resume with the exec-level `-s read-only -C` keeps the sandbox (*verified*: a write into the repo got "Operation not permitted"). The reply file is in the pass's own dir, which no other pass can write: Codex writes it itself, outside its sandbox, and would follow a symlink planted there. A turn that exits 0 without writing it is an empty reply, which fails validation and so gets the retry turn. `--ignore-user-config` alone still loads `~/.codex/AGENTS.md` (*verified*); the clean home does not (*verified*). Open items: `-m gpt-6.1-sol` was rejected in a clean home with a ChatGPT login (default became `gpt-6-luna`); whether token refresh replaces the symlink.

**Environment.** A reviewer inherits only what its CLI needs to run and log in: `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR` (find the login, including the macOS keychain; give the sandboxed shell a shell and a temp dir), `LANG`, `LC_ALL`, `LC_CTYPE`, `LC_COLLATE`, `LC_MESSAGES`, `LC_MONETARY`, `LC_NUMERIC`, `LC_TIME`, `TZ`, `TERM`, `COLORTERM` (locale; the TUI under the orca runner), `HTTPS_PROXY`, `NO_PROXY` (either case), `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE` (reach the API from a proxied network); Claude also `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_OAUTH_TOKEN` (its subscription login); Codex gets only its run-scoped `CODEX_HOME` from rreview. Not `ANTHROPIC_API_KEY`: Claude Code then reports `api_key` instead of `claude.ai` and bills the API (§1). Credentials that do reach the CLI, and so the reviewer, when the user sets them: a proxy URL's user and password, and the Claude OAuth token. Everything else, such as a `GH_TOKEN` set for rreview's `gh`, is dropped. Headless: the CLI starts with a cleared environment plus the listed names. Orca: the terminal's environment is Orca's and its login shell's, not rreview's, and a shell cannot drop all of it (a read-only export, a name that is no identifier, an exported function; zsh aborts the line on `unset` of a read-only variable), so the agent starts through a shim `<runroot>/scratch/<role>/bin/<program>` (a `/bin/sh` script, outside every pass's writable dir) that hands it to the hidden `rreview exec-reviewer --inherit <name> ... --set NAME=value ... -- <program> <args>`: it clears the environment, keeps each listed variable that is set and the launch's own env, and replaces itself with the program, so inherited values stay in the environment and never appear in an argv. The typed line is `PATH='<shim dir>':"$PATH" exec '<program>' ...`; no value goes on it, which the shell may keep in its history. A run dir whose path holds a `:` is refused (exit 2): it would split that PATH entry and the shell would start the real program with the terminal's whole environment. (*verified* live on both runners: the reviewer process held only listed names; Orca still recognizes and pastes to Claude and Codex). Orca itself adds `-c shell_environment_policy.set.ORCA_*` (pane, terminal, workspace ids, its data dir) to a Codex launch, so a Codex reviewer's shell sees those under the orca runner (*verified*; #29). A `--version` probe still runs with rreview's environment; it is no reviewer turn.

**Repo-provided text** (AGENTS.md, CLAUDE.md, `.agents/checks`) may still be read as code. Prompts state it is untrusted evidence.

## 4. Runners

One interface, two implementations:

```
run(pass) -> raw text      // pass = {role, agent, model, effort, prompt, cwd, timeout, outFile}
wrapUp(pass, message) -> raw text   // "time is up, reply with the JSON now"
```

- **headless** (default): `claude -p --output-format json` / `codex exec -o`. The reply is Claude's `result` (a failed exit or `is_error` fails the pass) or Codex's `-o` file. Each agent runs in its own process group; a timeout kills the whole group and the error names the pass. Wrap-up resumes the session (`claude -p --resume <id>`, `codex exec resume <thread-id>`). Logs: `<runroot>/logs/<role>.{stdout,stderr}`, and `<role>-turn<n>.*` for each wrap-up or retry turn.
- **orca** (variant 5), only with the Orca app running: before any work, within the review's budget, `orca status` must report the app running and its runtime reachable, and `orca repo show --repo path:<main checkout>` must find this repository (a reachable runtime can lack it), otherwise exit 2. It needs no Orca terminal (`ORCA_TERMINAL_HANDLE`): the runner uses only `orca worktree` and `orca terminal` commands, which work from any process of the user's, the Orca plugin's worker included (*verified*, Orca 1.4.262). The review worktree is Orca-created: `orca worktree create --repo path:<main checkout> --name rreview-<pr>-<sha12>-<pid>-<unix-seconds> --branch rreview/<same> --base-branch <head-sha> --setup skip` (setup hooks would run the PR's code), within the review's budget. The pid and start time make the name the run's own, so two runs for one PR head in one repository never share a worktree or branch, and neither run's cleanup reaches the other's. That branch must not exist before the run (a leftover stops it), so whatever carries it afterwards is the run's own: the cleanup guard is armed before the create and finds the worktree through `git worktree list` by that branch, so a create whose reply was lost is cleaned up too; the host checks the worktree's HEAD and that Orca made the requested branch. Removal: `orca worktree rm --force` (`git worktree remove --force` for a worktree Orca never registered), then `git branch -D` of that branch, unless `--keep-worktree`. Per pass, in its own `<runroot>/scratch/<role>` as for headless: `orca terminal create --worktree path:<wt> --title rreview:<role> --command "PATH='<scratch>/bin':\"$PATH\" exec '<program>' '<arg>' ..."` (the same isolated command, interactive, every word single-quoted, through the §3 environment shim; the program must be `exec`'s first word: with `exec env ...` or `exec '<path>/<program>'` Orca names the agent but its `send` reports provider `unsupported` and types the prompt raw, *verified*); `orca terminal show` until Orca reports the pass's agent as the terminal's `agentIdentity`, then `orca terminal wait --for tui-idle`. Nothing is typed before that: until Orca recognizes the agent it types text raw, into the shell before the agent starts and with every newline an Enter afterwards (*verified*: a starting Codex TUI satisfied `tui-idle` before Orca recognized it, and a prompt sent then arrived as raw lines; `send` reported `provider: unsupported`, which the runner now treats as a failure). `exec` leaves no shell behind the agent. `orca terminal send --text <message> --enter`; `wait --for tui-idle` again; then read `scratch/<role>/out/reply.txt`, which the reviewer writes itself (it may write only that `out/`; a symlink or FIFO there is refused); the host validates it and publishes `<runroot>/out/<role>.json`. The message starts with the delivery instruction, before the prompt, whose last part is the PR's untrusted text; control bytes are dropped from it. An agent idle without the file gets one reminder, then the pass fails. Each phase (first turn, wrap-up, retry) has one absolute deadline that bounds every Orca call in it, `send` included (an Orca call still running at the deadline is killed); a `wait` answer that arrives after the deadline counts as a timeout, whatever it says. At the pass timeout the wrap-up is typed into the same terminal; a reply that fails validation gets its retry turn there too; a wrap-up or retry past its own timeout closes the terminal and fails the pass. A terminal stays open between turns; it closes when its pass fails, else when the run ends, and one whose close fails stays registered and is closed again at the end. Do **not** use `orchestration worker-start`/`worker_done`: `worker_done` cannot reach the Orca runtime from inside the sandbox (EPERM, *verified*).
  - Claude's trust dialog shows in an Orca-created worktree too, unless the repository's main checkout is already trusted (*verified*, Orca 1.4.262 with a per-account Claude config); `wait` reports it as `blockedReason: agent-trust-workspace`, and the runner answers "Yes, I trust this folder" once, before the prompt. That matches headless `claude -p`, which skips the dialog; `--safe-mode` still keeps out the worktree's project customizations. Known limit: the answer persists in the user's Claude config (`.claude.json` under `$CLAUDE_CONFIG_DIR` or `~`, a `hasTrustDialogAccepted` project entry), so later Claude sessions there skip the dialog as well. Orca has a per-repository `agentWorkspaceTrust: pre-trust` setting, but neither `orca repo set` nor `orca worktree create` exposes it, and pre-trusting writes the same entry.
  - Claude runs with the §3 settings plus `--permission-mode acceptEdits --add-dir <scratch>/out`: the reply is a sandboxed Bash redirect into `out/`, which Claude otherwise asks about. Not `dontAsk`: on a live pass it refused the reviewer's heredoc reply twice (*verified*). A permission dialog stops a pass: `tui-idle` does not report it as blocked, so the pass waits until its timeout and the wrap-up is typed into the dialog (*verified* with a WebSearch, now denied in §3; detecting other dialogs: #28). The deny rules remove Edit and Write, and the sandbox refuses every write outside `out/` (*verified* live in this launch mode: Edit and Write were absent; `git commit`, `git branch` and writes into the worktree and `$HOME` failed with EPERM).
  - Codex's `-s read-only` blocks every write, the reply file too. The Codex TUI runs `codex -C <scratch>/out -s workspace-write -a never -c sandbox_workspace_write.exclude_slash_tmp=true -c sandbox_workspace_write.exclude_tmpdir_env_var=true` in the pass's clean `CODEX_HOME`: `out/` is its only writable root, it reads the worktree by absolute path, and `-a never` returns a refused command instead of asking (*verified* live in this launch mode: writes into the worktree, the git common dir, `$HOME` and `/tmp`, `git commit` and `git branch` failed; a write into `out/` worked; the user's `~/.codex/AGENTS.md` did not reach the session). Inside a git checkout the Codex TUI stops at its own trust prompt, which rreview does not answer, so a run with a Codex pass refuses a run dir inside a checkout (set `XDG_STATE_HOME` elsewhere).

Panel passes run in parallel (max 3, one thread each); coordinator and judge run in sequence. Budget: a per-pass timeout (`--timeout`, default 900 s) plus a total budget (`--budget`, default 3600 s); the budget starts before preparation, whose subprocesses (`gh`, `git` fetch and checkout, version probes) run in their own process group, killed at the deadline, and do not start after it (exit 2); every pass's timeout, wrap-up and retry are capped at what is left of the budget, and a pass with no budget left does not start (it fails). A pass killed at its timeout gets one wrap-up turn (at most 180 s). A reply that fails validation gets one more turn, which resumes the session with the validation error (at most 180 s); a CLI that failed (exit status, Claude's `is_error`) is not retried. After that the pass has failed.

## 5. Data contract

All outputs live in `<runroot>`; a review prints `run dir: <runroot>` to stderr as soon as the dir exists, before any pass, and again at the end:
- `meta.json`: PR, base, head, runner, role-to-agent map, versions of claude/codex.
- `progress.jsonl`: one line per event `{ts, role, status: started|wrapup|retry|completed|failed, agent, model, duration_ms, error?}`; `ts` is Unix epoch milliseconds, `duration_ms` counts from the pass's start, `model` is the role's `--role-model` or `default`. A `retry` event's `error` is the validation error that caused it. Roles: `intent_contracts`, `reliability`, `security`, `coordinator`, `judge`. The plugin tails it.
- `out/<role>.json`: the validated reviewer JSON (panelist envelope, coordinator review, judge array) following block/review's shapes (`panelistShape`, finding schema with `title`, `body`, `priority` 0-3, `confidence_score`, `code_location`), normalized by the host. It exists only for a pass whose reply passed validation. `out/` belongs to the host: reviewers write only into their own `scratch/<role>/`, so no pass can touch another's published reply. A panelist candidate locates itself with `path`, `line_start`, `line_end`.
- Coordinator reply: `{findings: [{title, body, confidence_score, priority, code_location, candidate_ids}], dropped_candidates: [{candidate_id, drop_reason: disproved|speculative|deterministic_ci|below_bar, evidence}], overall_correctness, overall_explanation, overall_confidence_score, review_process}`. Judge reply: `[{candidate_id, title, body, confidence_score, priority, code_location}]`.
- `result.json`: `{findings, ungated_findings, dropped_candidates, overall_correctness, overall_explanation, review_process, base, head, passes, degraded}` (block/review `Result`), written only when the coordinator completed. A finding is `{title, body, file, start_line, end_line, priority, confidence_score, stage: coordinator|judge, candidate_ids}` with a repo-relative `file` and the `[Pn]` tag cut from the title; a dropped candidate is `{id, title, panelist, file, line_range, priority, confidence_score, claim, drop_reason, evidence}`, filled by the host from the panel candidate plus the coordinator's reason and evidence; a pass is `{role, agent, model, effort?, status: completed|failed, duration_ms, error?}`. `degraded` is true when a panelist or the judge failed.
- Validation: strict decoding of the whole reply against its declared shape (an object for an envelope or review, an array for the judge), bare or inside one ```` ```json ```` fence with prose around it, nothing else; unknown fields rejected; one malformed candidate rejects the envelope; paths must be repo-relative and inside the diff's files (`git diff --name-only base head`, matched exactly). The same holds for the coordinator's review and the judge's array: a finding's `code_location.absolute_file_path` may also be an absolute path inside the review worktree; `priority` and `confidence_score` are required; a struct sent as a positional array or a repeated key is rejected.

## 6. CLI

```
rreview <pr-number|url> [--repo owner/name] [--head sha] [--runner headless|orca] [--author claude|codex]
        [--role-agent role=agent]... [--role-model role=model]... [--role-effort role=effort]...
        [--context-file path] [--gate p<=2,conf>=0.5 | --all] [--json] [--keep-worktree]
        [--timeout secs] [--budget secs] [--only role]
rreview show <runroot|pr> [--repo owner/name] [--json]   # print result of the latest run
rreview doctor                   # claude/codex/gh/orca versions, logins, sandbox self-test
```

`--timeout` is the per-pass timeout (default 900 s); a pass that hits it gets one wrap-up turn of at most 180 s. `--budget` is the whole review's (default 3600 s). `--head` reviews that commit (a full id, one of the PR's commits; GitHub lists at most 250) instead of the PR's current head; the run dir is named after it. A missing commit is fetched with the whole PR ref and base branch, which brings the PR's later commits into the repository too; so does resolving a merged PR's base, which needs the merge commit. A review that must not see later commits needs the head and base commits present beforehand and, for a merged PR, `gh pr view` answering with the pre-merge base as an open PR would; `docs/calibration.md` shows how. `--context-file` is the task's acceptance criteria, read by the intent lens and the coordinator. `--only <role>` runs one panelist alone, without coordinator, judge or `result.json` (a development flag; exit 0 when it completed, else 2). `--runner` takes only `headless` until the Orca runner lands. `rreview show` reads `<runroot>/result.json`, or for a PR the newest `result.json` among its run dirs, and prints it like the review did, with the same exit code.

`rreview doctor` runs the isolation self-test on a throwaway repo and a detached worktree of it, through the same launch builders a review uses: a write into the worktree, a commit and a branch must fail, `git diff` must work, a planted project hook must not fire, Codex must not load the user's AGENTS.md. Checks need the effects on disk and tool-side evidence to agree, never the reviewer's reply alone: Claude's probe writes its exit codes to `out/`, Codex's run must show the probe in its `--json` event log. The planted hook has a positive control at no model cost: the same Claude launch without `--safe-mode` and with an empty `CLAUDE_CONFIG_DIR` (no user config, no login) must fire it. The AGENTS.md probe gives Codex a stand-in `HOME` whose `.codex/AGENTS.md` names a random canary that must not appear in the reply, plus a control run whose clean `CODEX_HOME` holds a canary that must appear; the user's own `~/.codex` and `~/.claude` are never touched. It prints one line per check (`ok`, `FAIL`, or `warn` for the optional `orca`) and exits 0 only when every required check passes, else 1. This turns section 3's *verified* facts into a check that runs on every machine and every CLI upgrade.

## 7. Orca plugin (variant 6), after the CLI

A `trusted-worker` plugin in `orca-plugin/` (TypeScript, no build step; Node `child_process`/`fs` in its worker; confirmed in community plugins `klcd/agent-cli-permissions` and `Geromendez135/orca-pr-review`):
- Panel: the PR of the focused workspace (`gh pr view` in its folder, or a PR number or URL typed into the panel), button "Run review", runner choice (headless or orca).
- The worker runs `rreview <pr-url> --runner <r> --json` as a child process in the workspace's folder, learns the run dir from the first `run dir:` line on stderr, tails `progress.jsonl`, and takes the result from the exit code and the JSON on stdout (exit 2, a signal, or stdout that is not a valid result is a failed review); it renders findings as a file tree with line findings (UI pattern from `orca-pr-review`, MIT). The worker's environment is Orca's, not a terminal's: no `ORCA_TERMINAL_HANDLE`, which the orca runner does not need (§4). An optional GitHub account setting passes that `gh` account's token as `GH_TOKEN` to the gh and rreview child processes only.
- Progress is read only while the run dir is still this run's (its `dev:ino` when named), one bounded read at a time. Posts and stored state carry the run's status and counts only; the panel fetches the result, cut to Orca's message limits, and the full text stays in `result.json`.
- "Send to author": the person chooses an agent of the reviewed run's workspace (`agents.list`). The worker writes the selected findings, marked as review evidence, to `<runroot>/author-<time>.md`, refuses unless that terminal still runs the same agent session (`sessionId`) in that workspace, and types one fixed line naming the file with the worker's host API `terminal.sendText` (capability `terminal:send`); reviewer text is never typed into a terminal. This is not an orchestration send, so it needs no `--from`.

## 8. Milestones

1. Skeleton: Rust workspace, `rreview doctor` with the isolation self-test, CI (`cargo fmt --check`, `clippy -D warnings`, `cargo test`).
2. Headless runner + one panelist end to end on a fixture repo, strict JSON parsing, `progress.jsonl`.
3. Full pipeline: three lenses, coordinator, judge, gate, `result.json`, exit codes, wrap-up and retry.
4. Orca runner.
5. Orca plugin.
6. Calibration on 3-5 already-reviewed PRs against the existing cross-model review; tune the gate.

Each milestone is a GitHub issue with acceptance criteria; tests use fake `claude`/`codex` binaries on `PATH` (cheap checks first), with one opt-in live test per agent.
